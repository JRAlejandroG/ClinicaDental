1 Introducción
Una institución de salud requiere implementar un sistema informático que permita administrar de manera eficiente el inventario de insumos clínicos, asegurando la disponibilidad de productos, el control de vencimientos y la optimización del proceso de abastecimiento. El sistema debe entregar información actualizada en tiempo real sobre el stock existente y generar alertas automáticas que apoyen la toma de decisiones administrativas.
2 Objetivo General
Desarrollar un sistema de inventario que permita gestionar y controlar de manera eficiente los insumos clínicos, garantizando la disponibilidad de productos, reduciendo las pérdidas por vencimiento y mejorando la planificación de compras.
3 Objetivos Específicos
Registrar y mantener actualizado el stock de insumos clínicos.
Controlar las entradas y salidas de productos en tiempo real.
Configurar niveles mínimos de stock para cada producto.
Gestionar las fechas de vencimiento de los insumos almacenados.
Generar alertas automáticas por bajo stock y vencimientos próximos.
Facilitar la generación de órdenes de compra para la reposición de productos.
Mantener un historial completo de los movimientos realizados en el inventario.
Proporcionar información confiable para apoyar la toma de decisiones administrativas.

5 Requerimientos Funcionales
5.1 RF01 – Gestión de Productos
El sistema deberá permitir registrar, modificar, consultar y desactivar productos del inventario.
5.2 RF02 – Control de Stock
El sistema deberá actualizar automáticamente las existencias cada vez que se registre una entrada o salida de productos.
5.3 RF03 – Stock Mínimo
El sistema deberá permitir definir un stock mínimo para cada producto y monitorear su cumplimiento.
5.4 RF04 – Registro de Vencimientos
El sistema deberá almacenar y controlar la fecha de vencimiento de cada lote de productos.
5.5 RF05 – Alertas de Bajo Stock
El sistema deberá generar alertas cuando la cantidad disponible de un producto sea inferior al stock mínimo definido.
5.6 RF06 – Alertas de Vencimiento
El sistema deberá notificar cuando un producto esté próximo a vencer, según un período configurable.
5.7 RF07 – Órdenes de Compra
El sistema deberá generar órdenes de compra editables para la reposición de productos necesarios.
5.8 RF08 – Historial de Movimientos
El sistema deberá registrar todas las operaciones realizadas sobre el inventario, incluyendo ingresos, salidas, ajustes y anulaciones.
5.9 RF09 – Consultas y Reportes
El sistema deberá permitir consultar el stock actual, los productos bajo stock mínimo, los productos próximos a vencer, el historial de movimientos y las órdenes de compra emitidas.
6 Requerimientos No Funcionales
RNF01 – Seguridad
El sistema deberá utilizar autenticación para permitir el acceso
6.2 RNF02 – Disponibilidad
Deberá estar disponible durante el horario operativo de la institución
6.3 RNF03 – Usabilidad
La interfaz deberá ser intuitiva y fácil de utilizar por personal administrativo y clínico.
6.4 RNF04 – Rendimiento
Las consultas de inventario deberán responder en menos de 3 segundos.
6.5 RNF05 – Integridad de Datos
Toda transacción deberá registrarse garantizando la consistencia y auditoría de la información.

Criterio
Justificación
Consistencia de los datos
El motor InnoDB trabaja con transacciones ACID, lo que asegura que el stock nunca quede en un estado intermedio si una operación falla (RNF05).
Reglas de negocio en la BD
Soporta claves foráneas, restricciones CHECK, triggers, vistas y procedimientos almacenados, que usamos para proteger el inventario aunque la aplicación tenga un error.

Se conecta con Node.js mediante la librería mysql2, que permite consultas parametrizadas para prevenir inyección SQL.
Costo y despliegue
Es gratuito y de código abierto, y la base puede trasladarse sin cambios desde el entorno local al servidor institucional descrito en la vista física (Figura 9).
Conocimiento del equipo

16.4 Integridad de los Datos
Todas las tablas cuentan con una clave primaria autoincremental y las relaciones se implementan con claves foráneas, de modo que no es posible, por ejemplo, registrar un movimiento de un producto inexistente. Además, definimos restricciones UNIQUE para los datos que no pueden repetirse (correo del usuario, código del producto, RUT del proveedor y número de lote dentro de un mismo producto) y restricciones CHECK que impiden cantidades negativas, estados no permitidos o lotes cuya fecha de vencimiento sea anterior a la de ingreso.
Para cumplir el tiempo de respuesta exigido en el RNF04, agregamos índices sobre los campos más consultados: la fecha de vencimiento de los lotes, la fecha de los movimientos y el estado de las alertas. Por otra parte, los productos, usuarios y proveedores nunca se eliminan, sino que se desactivan mediante su campo estado, con lo que se conserva el historial completo del inventario.
16.5 Lógica Implementada en la Base de Datos
Además de las tablas, incorporamos en la base de datos las reglas más importantes del negocio, para que se cumplan siempre, independientemente de la aplicación que acceda a ella:
Objeto
Tipo
Función
trg_movimiento_bi
Trigger
Antes de registrar un movimiento, valida que el lote corresponda al producto, que haya stock suficiente y que los ajustes tengan motivo. Luego actualiza automáticamente la cantidad del lote (RF02).
trg_movimiento_bu / trg_movimiento_bd
Trigger
Impiden modificar o eliminar movimientos, de modo que el historial funciona como registro de auditoría (RNF05).
v_stock_actual
Vista
Calcula el stock total y el disponible (sin lotes vencidos) de cada producto.
v_productos_bajo_minimo
Vista

v_lotes_por_vencer
Vista

v_historial_movimientos
Vista
Muestra el historial con nombres legibles de producto, lote y usuario (RF08).
sp_generar_alertas
Procedimiento
Genera las alertas de bajo stock y vencimiento sin duplicar las pendientes. Es el que ejecuta la tarea programada de la vista de procesos (Figura 8).
Con este diseño, el stock nunca se modifica directamente: un lote se crea con cantidad cero y su cantidad cambia únicamente mediante movimientos. Si un movimiento se registró por error, no se borra, sino que se registra una anulación que revierte su efecto y queda asociada al movimiento original. Así, el inventario siempre puede reconstruirse a partir del historial.
16.6 Seguridad en la Base de Datos
Las contraseñas se almacenan como hash generado con bcrypt, nunca en texto plano, y la cuenta se bloquea temporalmente tras cinco intentos fallidos (valores definidos en la tabla configuracion). La aplicación se conecta a la base con un usuario propio, inventario_app, que solo tiene permisos de lectura, inserción, actualización y ejecución de procedimientos, pero no de eliminación, aplicando el principio de mínimo privilegio.
